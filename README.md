# Website Trust Assessment System

**Evidence-grounded, action-aware website trust assessment, built for local-first research.**

The system is a research prototype that assesses a website along four dimensions instead of returning a
single opaque "safe/unsafe" label:

| Dimension | Question it answers |
| --- | --- |
| Security & Fraud | Does the site show technical or behavioural signs of phishing, fraud, or unsafe handling of credentials? |
| Identity & Legitimacy | Is the site who it claims to be, and is there enough registration, transport, and content evidence to support that claim? |
| Privacy & Data | What data does the page collect or leak, and are consent and policy controls present? |
| Manipulation & Deception | Does the page pressure, obscure, or deceive the visitor? |

Every score decomposes into auditable evidence cards with provenance, severity, confidence, and
risk/trust contributions. The same site can receive different dimension weights depending on whether
the visitor is browsing, creating an account, or making a purchase. When the available evidence is too
weak, the system abstains rather than inventing certainty.

> **Status.** The engine, API, dashboard, browser extension, annotation workflow, dataset builder, and
> CPU-only training pipeline are implemented and tested. The `feed_v2` evaluation dataset is frozen
> (830 samples / 826 domains; 497 malicious, 333 benign), and its test-split artifacts are published
> under `data/research/runs/feed_v2/`. The 146 frozen human labels are a validity subset, not the
> primary labels. A train-only learning curve shows the models saturate at this dataset size. Frozen
> results are published under `data/research/runs/feed_v2/` and the figures are regenerated by
> `scripts/paper_artifacts.py`; the shipped decision policy remains the rule engine.

---

## Research questions

The system is designed around four questions that the current literature handles unevenly:

1. **The padlock paradox.** How often do malicious sites present valid HTTPS, and how much does a
   padlock by itself tell a user about trust?
2. **Multi-signal transfer.** Do page, domain, transport, privacy, and manipulation signals transfer
   across domains better than URL-only lexical models?
3. **Evidence over verdicts.** Do evidence cards with provenance improve appropriate reliance
   compared with a single risk score?
4. **Isolation from hostile page content.** Can a system detect instruction-like hidden content and
   keep it out of the scoring path, rather than letting a page influence an automated reviewer?

The full hypotheses, planned ablations, statistical analysis, and threats to validity are in
[docs/research-plan.md](docs/research-plan.md).

---

## What is implemented

- **Four-dimensional evidence model.** More than 70 evidence codes across URL structure, HTTP
  security headers, page content and forms, tracker behaviour, dark patterns, domain registration and
  DNS, TLS, policy pages, OCR, hidden-content injection, and local infrastructure reputation.
- **Action-aware aggregation.** Dimension weights differ for `browse`, `signup`, and `purchase`;
  critical findings and locally imported reputation labels apply explicit floors.
- **Calibrated abstention, not forced answers.** Per-dimension and overall confidence, source
  coverage, `unknown` levels, and optional score calibration. The rule score is never presented as a
  probability unless a calibration artefact exists.
- **Auditable explanations.** Deterministic headlines, rationales, recommendations, missing-evidence
  notes, and evidence IDs. No cloud model is required.
- **Safe crawling.** SSRF checks on every request and redirect, public-IP validation, bounded
  redirects and response size, no form submission, no downloads, blocked service workers, dismissed
  dialogs, and blocked media.
- **Local-first deployment.** FastAPI on `127.0.0.1`, SQLite storage, screenshots on disk, and a
  Manifest V3 extension that refuses to contact anything except localhost.
- **Research workflow.** Blinded two-annotator queues, Cohen's kappa (unweighted, linear, quadratic),
  adjudication, consensus labels, leakage-checked dataset construction, domain-grouped splits,
  grouped cross-validation, Platt calibration, validation-only threshold selection, untouched test
  evaluation, grouped bootstrap confidence intervals, risk-coverage analysis, and model/report
  artifacts.
- **CPU-only training.** Logistic regression, regularised HistGradientBoosting, and the rule engine
  baseline run on a 16 GB laptop without a dedicated GPU or paid API.

## Quick start

### Requirements

- Python 3.10 or newer (tested with Python 3.14 on Windows 11).
- 16 GB RAM is sufficient; a GPU is not required.
- Chromium installed through Playwright.
- Tesseract OCR is optional. Without it, OCR evidence is unavailable and coverage is reduced.
- Node.js is not required; the dashboard and extension are plain HTML/CSS/JavaScript.

### Install

```bash
python -m venv .venv
```

Windows (PowerShell):

```powershell
.venv\Scripts\Activate.ps1
```

Windows (Command Prompt):

```bat
.venv\Scripts\activate.bat
```

Windows (Git Bash) or macOS/Linux:

```bash
source .venv/Scripts/activate  # Windows Git Bash
source .venv/bin/activate      # macOS/Linux
```

Then:

```bash
python -m pip install --upgrade pip
pip install -e ".[dev]"
python -m playwright install chromium
wtas doctor
```

`wtas doctor` checks the interpreter, required packages, bundled knowledge and dashboard assets,
the extension, the writable data directory, SQLite, Chromium, OCR, and the server port. It exits
non-zero when a required check fails. The install provides the `wtas` command and the `wtas-api`
server entry point. A normal `pip install .` (without `-e`) is also supported: the
API and dashboard are bundled in the wheel, while writable state goes to the platform user-data
directory (`%LOCALAPPDATA%\WebsiteTrustAssessment` on Windows). Set
`WTAS_HOME` to choose another runtime directory. The browser extension is loaded from the source checkout.

Optional OCR:

- Windows: install Tesseract from the UB Mannheim builds and add its directory to `PATH`.
- Debian/Ubuntu: `sudo apt install tesseract-ocr`.
- macOS: `brew install tesseract`.

### Run

```bash
wtas doctor
wtas init
wtas scan https://example.com --action purchase
wtas serve
```

Open <http://127.0.0.1:8000/dashboard>. Interactive API documentation is at
<http://127.0.0.1:8000/docs>. For a scripted walkthrough, pre-demo checks, and troubleshooting, see
[docs/demo.md](docs/demo.md).

The first assessment of a domain is slower because Chromium launches and the page settles; cached
assessments are served for one hour by default.

### Install the browser extension

1. Start the local server with `wtas serve`.
2. Open `chrome://extensions` in Chrome or Edge.
3. Enable **Developer mode**.
4. Choose **Load unpacked** and select the `extension/` directory.
5. Pin **Website Trust Assessment Guard** and open the popup on any page.

The extension sends the current URL to `http://127.0.0.1:8000` only. It does not use a remote service.
The server address can be changed in the extension settings, but only `127.0.0.1` and `localhost`
hosts are accepted.

Example:

```bash

  -H "Content-Type: application/json" \

```

The API binds to localhost by default. Do not expose it to a network: it is designed to fetch
untrusted public pages on behalf of the local user.

## How scoring works

1. **Evidence.** Each extractor emits structured observations. Risk and trust points are already
   normalised within a dimension. Repeated codes are merged, keeping the strongest observation.
2. **Dimension scores.** The dimension risk is `sum(risk_points * confidence) - trust_points`, with
   trust capped at 12 and the result clipped to 0–100. Critical and high-severity evidence applies
   explicit floors so that a single decisive finding cannot be averaged away.
3. **Confidence and coverage.** Confidence blends evidence reliability with the fraction of expected
   evidence sources that were actually available. A dimension abstains when confidence and coverage
   are low, the score is below 35, and no strong evidence exists.
4. **Overall risk.** Active dimensions are combined with action-specific weights. Inactive dimensions
   do not silently contribute zero.
5. **Label floors.** Locally imported `malicious`/`suspicious` reputation labels raise both the
   security dimension and the overall score. These floors are recorded in `meta.floors` and are
   excluded from research training data.
6. **Calibration.** If `models/calibration.json` exists, the overall score is mapped to a calibrated
   probability. Otherwise `calibrated_probability` stays `null`. A rule score is not a probability.

Risk bands: `low < 25`, `medium < 50`, `high < 75`, `critical >= 75`, plus `unknown` for abstention.

Action weights:

| Action | Security | Identity | Privacy | Manipulation |
| --- | ---: | ---: | ---: | ---: |
| Browse | 0.45 | 0.20 | 0.15 | 0.20 |
| Sign up | 0.30 | 0.25 | 0.30 | 0.15 |
| Purchase | 0.35 | 0.35 | 0.15 | 0.15 |

## Research workflow

```bash
# 1. Collect assessments. Full JSONL is required for queue/dataset reproducibility.
wtas batch data/example_urls.csv --action browse --out data/exports/round1.jsonl --full

# 2. Build blinded annotator sheets. key.json is coordinator-only.
wtas research queue --out data/annotations/round1 \
  --assessments data/exports/round1.jsonl --overlap 0.2 --seed 42

# 3. Fill annotator_a.csv and annotator_b.csv independently, then check agreement.
wtas research agreement \
  --a data/annotations/round1/annotator_a.csv \
  --b data/annotations/round1/annotator_b.csv \
  --key data/annotations/round1/key.json \
  --out data/annotations/round1/agreement.json \
  --markdown data/annotations/round1/agreement.md

# 4. Build consensus labels. This also writes consensus_disagreements.csv.
wtas research merge \
  --a data/annotations/round1/annotator_a.csv \
  --b data/annotations/round1/annotator_b.csv \
  --key data/annotations/round1/key.json \
  --out data/annotations/consensus.csv

# 5. Fill adjudicated_label (and confidence/notes) in the disagreement sheet, then rerun.
wtas research merge \
  --a data/annotations/round1/annotator_a.csv \
  --b data/annotations/round1/annotator_b.csv \
  --key data/annotations/round1/key.json \
  --adjudication data/annotations/consensus_disagreements.csv \
  --out data/annotations/consensus.csv

# 6. Build a leakage-checked, domain-grouped dataset.
wtas research dataset \
  --out data/datasets/v1 \
  --assessments data/exports/round1.jsonl \
  --labels data/annotations/consensus.csv \
  --ratios 0.7,0.15,0.15 --seed 42 --per-domain-limit 5

# 7. Train, calibrate, and evaluate. The test split is touched once.
wtas research train \
  --dataset data/datasets/v1/dataset.jsonl \
  --out-dir data/research/runs --models-dir models/research \
  --groups url,signals,rule,hybrid --seed 42 --bootstrap 1000 --cv-folds 5 \
  --run-name v1

# 8. Re-evaluate a saved artifact on a chosen split.
wtas research evaluate \
  --model models/research/logistic_hybrid.json \
  --dataset data/datasets/v1/dataset.jsonl --split test --bootstrap 1000 \
  --out data/research/runs/v1/test_evaluation.json

# 9. Explain the test-split errors (no page is opened; the split is read, never re-fitted).
PYTHONPATH=. python scripts/error_analysis.py \
  --dataset data/datasets/v1/dataset.jsonl --models models/research \
  --exports "data/exports/feed/batch_0*.jsonl" --out data/research/errors.json
```

Step 9 re-derives each stored logistic artifact's per-sample probabilities and refuses to report anything
until the reproduced `tp/fp/fn/tn` matches the confusion the run recorded, so the examples come from the
same predictions the metrics were computed from. It classifies every error from the evidence codes and
feature values the capture actually recorded (page state, TLS, form presence, brand claim, tracker
surface, host shape) and hashes the domain of any negative-class example, because naming a small
legitimate site that a false alarm flagged adds risk without adding evidence.

The rerun in step 5 overwrites `consensus.csv` using the adjudicated labels. Unresolved disagreements
remain excluded from consensus and are recorded in the disagreement summary.

Round 2 uses a gated mixed-calibration manifest in `data/candidates/round2.csv`: 20 public-feed scam
candidates, 8 ambiguous sites, and 8 established controls. The manifest was built from feed metadata
only; no candidate page was opened. Rebuild it with:

```bash
wtas research candidates --out-dir data/candidates --seed 11
```

A normal batch collects only the 16 safe strata and prints how many gated rows it skipped. The 20
feed candidates are collected only after the team explicitly approves access, using
`--allow-gated` with the dedicated browser profile. Round 2 is not part of the default workflow
above until that approval and the annotation round are complete. See
[docs/annotation-protocol.md](docs/annotation-protocol.md) section 5.2.

### Main collection (single annotator)

The main collection follows [docs/main-dataset-protocol.md](docs/main-dataset-protocol.md). It uses
one human annotator, no double annotation, and a delayed blind 15% intra-rater audit. The candidate
manifest combines Tranco rank bands with public OpenPhish and URLhaus feed metadata:

```bash
wtas research main-candidates --out-dir data/candidates --seed 42
```

This writes 500 selected domains and 160 reserve domains. Gated feed rows are never opened by the
candidate builder. Collect and label one batch at a time so the assessment and label stay close:

```bash
wtas batch data/candidates/main_batch_01.csv \
  --out data/exports/main/batch_01.jsonl --full --resume

wtas research queue --out data/annotations/main/batch_01 \
  --assessments data/exports/main/batch_01.jsonl --single-annotator --seed 42

wtas research label-ui --sheet data/annotations/main/batch_01/annotator_a.csv \
  --snapshots data/exports/main/batch_01.jsonl

# Before freezing: transport-only triage of any "could not load" note, then the exclusion record.
python scripts/reachability_triage.py
python scripts/non_inspections.py

wtas research freeze \
  --sheet data/annotations/main/batch_01/annotator_a.csv \
  --key data/annotations/main/batch_01/key.json

wtas research main-status --markdown data/main_collection_status.md
```

`research main-status` rebuilds `data/main_collection_status.json` from the artefacts on disk: per-batch
collection failures, cross-domain redirect substitutions, queue size, label mix, freeze state, the
48-hour window, the gated-collection status, and integrity checks. It exits non-zero if a check fails.

Rows whose note records a failed load rather than an observation are never relabelled. They are written
to `non_inspections.csv` and dropped at dataset time, from the primary task and from the suspicious
sensitivity analysis:

```bash
wtas research dataset --out data/datasets/v1 \
  --assessments data/exports/main/batch_01.jsonl \
  --labels data/annotations/main/consensus.csv \
  --exclude-uninspected data/annotations/main/batch_01/non_inspections.csv
```

After all batches are frozen, build and run the delayed audit:

```bash
wtas research audit-queue \
  --sheet data/annotations/main/batch_01/annotator_a.csv \
  --key data/annotations/main/batch_01/key.json \
  --out data/annotations/main/audit/batch_01 --fraction 0.15 --min-domains 40 --seed 123

# Re-label annotator_a_audit.csv after the recorded not_before timestamp, then:
wtas research audit-report \
  --reference data/annotations/main/audit/batch_01/audit_reference.json \
  --audit data/annotations/main/audit/batch_01/annotator_a_audit.csv
```

The audit is intra-rater consistency, not inter-rater reliability. The 549-domain gated feed collection
was approved once and is complete; that approval is spent, so any new gated collection requires a fresh
explicit team decision.

### Feed-labeled primary evaluation

Per [docs/main-dataset-protocol.md](docs/main-dataset-protocol.md) section 2.2 the primary ground truth
is abuse-feed membership, and the frozen human labels are a validity subset. Build the label set from
the live feeds (or from saved snapshots for an offline rebuild):

```bash
wtas research feed-labels \
  --out data/labels/feed/labels.csv \
  --exclude-domains data/candidates/main_batch_01.csv \
  --exclude-domains data/candidates/main_reserve.csv \
  --exclude-domains data/candidates/round2.csv

# Rebuild from a saved copy instead of the network:
wtas research feed-labels --out data/labels/feed/labels.csv \
  --openphish-file data/labels/feed/snapshots/openphish.txt \
  --urlhaus-file data/labels/feed/snapshots/urlhaus.csv
```

This writes one `malicious` row per registrable domain plus a provenance manifest holding the feed URL,
the raw-body SHA-256, the retrieval timestamp, the accepted-entry count, and every rejection count. It
refuses to run on a feed older than `--max-age-days` (7 by default) and warns when a local snapshot has
no verifiable age. **Never** pass the result to `wtas import-labels`: loading it into the runtime
`domain_labels` store would let `known_malicious_label` evidence hand the model the verdict it is later
scored against.

After collecting assessments, assert that no verdict leaked before building the dataset:

```bash
# Assemble the gated crawl plan. This reads label metadata only; no page is opened.
wtas research feed-candidates --labels data/labels/feed/labels.csv \
  --out-dir data/candidates --seed 42

# Collection itself still needs a fresh explicit approval, i.e. `batch --allow-gated`.
wtas research feed-check \
  --labels data/labels/feed/labels.csv \
  --assessments data/exports/feed/batch_01.jsonl \
  --out data/labels/feed/leakage_check.json
```

The command exits non-zero when any assessment carries a leakage reason or any feed domain is present in
the runtime store. Collecting the feed slice still touches live malicious infrastructure and still
requires a fresh explicit approval; nothing here changes that gate.

To compare the two label sources on the domains they share (reports disagreements, never reconciles
them):

```bash
wtas research feed-agreement --labels data/labels/feed/labels.csv \
  --human-labels data/annotations/main/batch_01/labels.csv \
  --out data/labels/feed/human_vs_feed.json
```

At dataset time, join what was actually collected with feed membership to get the primary label file:

```bash
wtas research feed-eval-labels --labels data/labels/feed/labels.csv \
  --assessments data/exports/feed/batch_01.jsonl data/exports/main/batch_01.jsonl \
  --human-labels data/annotations/pilot/annotator_a.csv \
    data/annotations/round2/labels_v2.csv data/annotations/main/batch_01/labels.csv \
  --out data/labels/feed/eval_labels.csv
```

A collected domain in a feed becomes `malicious` and one absent from both feeds becomes `benign`, which
means "not reported", not "verified trustworthy". A feed domain that produced no assessment is dropped.
Domains that already carry a frozen human label are given **no** derived label, because feed absence
would otherwise silently turn a human-confirmed positive into a negative; they stay the validity subset.

The feed plan contains no negatives, so `--assessments` must also cover the safe main strata, which are
sampled from the pre-registered manifest before any verdict exists ([main-dataset-protocol.md](docs/main-dataset-protocol.md)
section 4.3). Passing only the feed exports produces a positive-only file that no classifier can be
trained on; `scripts/feed_crawl_remaining.sh` collects both pools and `scripts/feed_v1_build.sh` builds
the dataset and runs the model comparison over their union. `scripts/feed_v2_build.sh` is the current
driver: it builds `data/datasets/feed_v2` from every export, trains it, then repeats the run with split
seed 43 and with the main batch 02 negative stratum removed (`feed_v2_s43`, `feed_v2_no_batch_02`) so the
seed choice and the amendment that reuses those assessments as negatives are both measurable rather than
assumed, and finishes with gate compliance, the error analysis and the dataset profile.

A feed label is only true at its retrieval time. To measure that transience without touching the frozen
primary set, re-fetch into a separate artifact and compare the two label files by domain:

```bash
# Metadata-only fetch — no page is opened, and labels.csv is never overwritten.
wtas research feed-labels \
  --out data/labels/feed/churn/labels_t2.csv \
  --manifest data/labels/feed/churn/labels_t2.json \
  --snapshot-dir data/labels/feed/churn/snapshots

python scripts/feed_churn.py    # writes data/labels/feed/churn/churn_report.json
```

`feed_churn.py` reports retained / dropped / newly-listed counts overall and per source, and how many of
the domains the evaluation labelled positive a later retrieval still lists. It never re-labels anything:
dropped domains stay in the primary set, because the label was correct at collection time.

Approval scope is checked the same way rather than asserted. `scripts/gate_compliance.py` compares a
candidate CSV with the export produced from it and counts scored rows per `collection_gate`; pairs marked
`--ungated` fail if any gated row was scored. `bash scripts/gate_compliance_all.sh` runs it over every
batch in the evaluation and writes `data/research/gate_compliance.json`.

Composition and the shipped engine's behaviour are reported from the published dataset rows, not from ad
hoc counting, so a paper number can be regenerated with one command:

```bash
PYTHONPATH=. python scripts/dataset_profile.py \
  --dataset data/datasets/feed_v2/dataset.jsonl \
  --assessments "data/exports/feed/batch_0*.jsonl" "data/exports/main/batch_0*.jsonl" \
    data/exports/main/reserve.jsonl \
  --out data/research/profile_feed_v2.json
```

It gives class counts per split, HTTPS presence separately from trusted-chain rate (a certificate existing
and a certificate verifying are different claims), the engine's risk-band distribution over every labelled
row with recall at escalation, the engine AUROC over the full labelled set and per split, and the natural
prevalence of the hidden-injection and hidden-iframe surfaces. `data/datasets/feed_v2/artifacts_snapshot/`
freezes the labels, leakage check, export digests, profile, gate report and the three run artifacts cited
by [docs/paper-outline.md](docs/paper-outline.md), so a later crawl cannot move a published number.

H4 is measured offline on a locally authored fixture corpus, so no page is crawled and the SSRF guard is
never relaxed (loopback crawling is blocked by design, and it stays blocked):

```bash
# 1. Render 42 paired fixtures from 6 shared body templates. Deterministic, offline.
wtas research injection-build --out data/injection_fixtures

# 2. Score them twice (with and without the injection evidence) and run the isolation gate.
wtas research injection-eval --corpus data/injection_fixtures \
  --out data/research/injection_h4.json
```

Each case is scored through the production static parser, then re-scored with `INJECTION_CODES ∪
TRACE_CODES` dropped; the gate requires the stripped re-score to reproduce the clean baseline *exactly*,
so a hidden instruction that leaks into any other feature fails the run instead of quietly passing. The
command exits non-zero when any gate check fails.

The dataset loader excludes assessments that already contain a known reputation label, a label-derived
floor, or label-derived infrastructure neighbours. This prevents blocklist information from leaking
into features. Suspicious labels are excluded from the primary binary task; use
`--include-suspicious` for a sensitivity analysis.

## Safety and privacy

- Page content is **data, not instructions**. The system does not send raw HTML to a language model and
  does not execute page-provided commands. Hidden instruction-like text is detected and reported.
- Forms are inspected but never submitted. Passwords, card numbers, OTPs, and seed phrases are never
  entered.
- Downloads, service workers, popups, and media are blocked. Dialogs are dismissed.
- Every browser subrequest and redirect is checked against private, loopback, link-local, and
  metadata-address ranges. DNS rebinding remains a residual risk; see
  [docs/threat-model.md](docs/threat-model.md).
- Assessment data, screenshots, labels, and feedback stay in local SQLite and local files. There is no
  telemetry, cloud inference, or paid API.
- The browser extension requires broad host permissions to detect the active tab, but it transmits
  only the current URL to localhost. Review `extension/background.js` before installing.

## Limitations

- This is an advisory research prototype, not a malware scanner, a guarantee of safety, or a
  compliance tool.
- Client-side cloaking can show a headless browser different content from a human visitor.
- Static fallback without Chromium produces reduced evidence; coverage and confidence reflect this.
- The crawler intentionally ignores TLS certificate errors so it can collect evidence from
  misconfigured or phishing pages. The certificate failure is then reported as evidence.
- The dataset is a convenience sample, not a prevalence-representative sample of the web.
- Domain reputation labels are user-supplied and can be stale or wrong; they are excluded from model
  training by default.
- No system that observes a page from the outside can prove that a page is safe.
